## The feature: "Pack for your destination"

In the app, under the chat: **👗 Pack for <city>**.
1. Consent checkbox, then upload a photo. The photo stays in memory only and goes to YouCam just for the request.
2. **Try it on:** pick one of YouCam's outfit templates (free list), and YouCam Apparel VTO renders you wearing it. **2 units.**
3. **Skin check for the trip:** 4 SD concerns (moisture, oiliness, redness, radiance) give 0–100 scores, cosmetic packing tips, and the destination's weather this week via Tavily, with sources. **9 units.**

## Verified API facts

| Item | Verified value |
|---|---|
| Base / auth | `https://yce-api-01.makeupar.com`, `Authorization: Bearer $YOUCAM_API_KEY`. `YOUCAM_SECRET_KEY` is **not needed** for v2 (legacy v1 auth) and is never read |
| Balance (free) | `GET /s2s/v1.0/client/credit` → `results[].amount_dec` |
| Price list (free) | `GET /s2s/v2.0/credit/feature-cost` (paginated `skus`: `amount` per `proc_unit`, `run_task_url`) |
| Unit history (free) | `GET /s2s/v1.0/client/credit/history`. **Needs `Content-Type: application/json`** even on GET, otherwise HTTP 415 |
| Upload (free) | `POST /s2s/v2.0/file` `{files:[{content_type, file_name, file_size}]}` → `data.files[0].file_id` + `requests[0]` (`method`, `url`, `headers`); then PUT the bytes. Max 10 MB |
| Outfit templates (free) | `GET /s2s/v2.0/task/template/cloth?page_size=` → `data.templates[]` `{id, title, thumb, category_name}` |
| **Apparel try-on** | `POST /s2s/v2.0/task/cloth`: `src_file_id` \| `src_file_url` **plus** `template_id`, **or** `ref_file_url` \| `ref_file_id` + `garment_category` (`full_body`/`lower_body`/`upper_body`/`shoes`/`auto`). Optional `change_shoes`. Poll `GET /s2s/v2.0/task/cloth/{task_id}` → `data.task_status`, then `data.results.url` (pre-signed, about 2 h) |
| **Skin analysis** | `POST /s2s/v2.0/task/skin-analysis`: `src_file_id` \| `src_file_url`, `dst_actions` (all SD *or* all HD), `format: "json"`. Poll `GET …/{task_id}` |
| Billing rule | Units are charged at task creation and **automatically refunded if the task fails** (history shows `…_failed` refunds), so a failed task costs 0 net |

## Is the 440 floor effective on the hosted demo?

**Yes, by construction. It doesn't use any local state:**
- The floor is a code constant (`HARD_MIN_BALANCE = 440`). `TASTEBOUND_YOUCAM_MIN_BALANCE` can only *raise* it.
- Before every paid task, `_preflight` calls `floor_status()`, which reads the **real balance** from YouCam (`GET /s2s/v1.0/client/credit`, never cached). This happens before the local ledgers are touched.
- If the balance read fails, no task is created (fails closed).
- "Read balance → create task" is serialized by a process-wide lock, so concurrent sessions can't both pass on the same balance.
- Tests: `test_real_balance_floor_blocks_even_with_fresh_ledger`, `test_floor_does_not_depend_on_local_state`, `test_balance_read_failure_fails_closed`.

**How to verify online (0 units):**
1. **Positive check:** unlock 🔐 Operator in the hosted app. The *Live safety checks* line shows `YouCam: balance … · floor 440 · ✅ active`, produced by the same `floor_status()` that guards paid tasks.
2. **Negative check:** temporarily add `TASTEBOUND_YOUCAM_MIN_BALANCE = 100000` to Streamlit secrets (raising is allowed). Try one outfit: it must show "demo limit reached", the operator line must show `⛔ blocking`, and the balance (free call) must be unchanged. Then remove the override.
